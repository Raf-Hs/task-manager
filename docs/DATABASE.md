# Modelo de datos

Base de datos de **Task Manager**: una sola tabla, `tasks`, sobre PostgreSQL.

- **Motor**: PostgreSQL 17
- **Migraciones**: pendientes de incorporar Flyway (ver
  [ADR-0009](adr/0009-flyway-over-ddl-auto.md))
- **Herramienta**: Hibernate 6 con `ddl-auto=update` en desarrollo

---

## 1. Diagrama

```
┌──────────────────────────────────────────────────────────────┐
│                          tasks                               │
├──────────────┬───────────────┬───────────────────────────────┤
│ Columna      │ Tipo          │ Reglas                        │
├──────────────┼───────────────┼───────────────────────────────┤
│ id           │ bigint        │ PRIMARY KEY, identity         │
│ title        │ varchar(200)  │ NOT NULL                      │
│ description  │ varchar(2000) │ NULL                          │
│ due_date     │ date          │ NULL                          │
│ priority     │ varchar(10)   │ NOT NULL, CHECK (LOW|MEDIUM|  │
│              │               │ HIGH)                         │
│ completed    │ boolean       │ NOT NULL                      │
│ created_at   │ timestamptz   │ NOT NULL, solo escritura      │
│ updated_at   │ timestamptz   │ NOT NULL                      │
└──────────────┴───────────────┴───────────────────────────────┘
```

No hay claves foráneas: solo hay una tabla, y añadir una apuntando a la propia
tabla no aportaría nada.

## 2. Columnas

### `id`

| | |
| --- | --- |
| Tipo | `bigint` |
| Restricciones | `NOT NULL`, PRIMARY KEY |
| Generada | `GENERATED BY DEFAULT AS IDENTITY` |
| Valor por defecto | El que asigna la secuencia |

El identificador lo asigna la base de datos, nunca el cliente. La entidad JPA
usa `GenerationType.IDENTITY`, así que el `INSERT` pide el valor a PostgreSQL
y no necesita una segunda consulta.

### `title`

| | |
| --- | --- |
| Tipo | `varchar(200)` |
| Restricciones | `NOT NULL` |

Es el nombre de la tarea y la única referencia que el usuario tiene de ella.
La misma regla se aplica en la base de datos (`NOT NULL`) y en la aplicación
(`@NotBlank` + `@Size(max = 200)`).

### `description`

| | |
| --- | --- |
| Tipo | `varchar(2000)` |
| Restricciones | admite `NULL` |

Opcional. Una cadena en blanco se guarda como `NULL`: la capa de servicio la
normaliza, para que en la base de datos no haya textos vacíos disfrazados de
contenido.

### `due_date`

| | |
| --- | --- |
| Tipo | `date` |
| Restricciones | admite `NULL` |

Fecha límite de la tarea. Solo la parte de la fecha: no hay hora, porque una
tarea no vence a las 14:30.

**No se rechaza una fecha en pasado.** Una tarea con fecha límite caducada
sigue siendo válida: es una tarea *vencida*, que la interfaz marca y que las
estadísticas cuentan aparte. Es un estado legítimo, no un error.

### `priority`

| | |
| --- | --- |
| Tipo | `varchar(10)` |
| Restricciones | `NOT NULL`, `CHECK (priority IN ('LOW', 'MEDIUM', 'HIGH'))` |
| Valor por defecto | `MEDIUM` (lo aplica la aplicación) |

Se guarda como **texto** y no como número. Motivos:

- La base de datos sigue siendo legible: `HIGH` dice más que `3`.
- El orden no depende de la representación. Si mañana se añade un nivel
  `CRITICAL`, no hay que renumerar nada.
- El `CHECK` impide que entren valores que la aplicación no conoce, aunque
  alguien escriba en la base de datos a mano.

El `CHECK` lo genera Hibernate a partir del enum de Java, así que la base de
datos y el código no se pueden desincronizar sin que se note.

### `completed`

| | |
| --- | --- |
| Tipo | `boolean` |
| Restricciones | `NOT NULL` |
| Valor por defecto | `false` |

Marca si la tarea está terminada. Es un `boolean` y no un estado con tres
valores (`PENDING`, `DONE`, `ARCHIVED`) porque el proyecto solo necesita saber
si la tarea está hecha o no.

### `created_at`

| | |
| --- | --- |
| Tipo | `timestamp(6) with time zone` |
| Restricciones | `NOT NULL`, no se puede actualizar |

Momento de la creación. Lo fija el servidor en el `@PrePersist` de la entidad,
así que el cliente no puede mandarlo.

### `updated_at`

| | |
| --- | --- |
| Tipo | `timestamp(6) with time zone` |
| Restricciones | `NOT NULL` |

Momento de la última modificación. Lo fija el servidor en el `@PreUpdate` de
la entidad. Sirve para ordenar por "modificados recientemente" y para saber si
un recurso ha cambiado desde la última lectura.

## 3. Tipos de PostgreSQL y por qué

| Tipo en Java | Tipo en PostgreSQL | Motivo |
| --- | --- | --- |
| `Long` | `bigint` | Un `integer` se quedaría corto en cuanto la tabla creciera; `bigint` llega hasta 9 223 372 036 854 775 807. |
| `String` | `varchar(n)` | El límite se pone en el esquema, no solo en la validación, para que un `INSERT` directo tampoco pueda saltarse la regla. |
| `LocalDate` | `date` | Una fecha límite es un día del calendario, sin hora ni zona. |
| `Instant` | `timestamptz` | Una marca de tiempo es un instante absoluto. `timestamptz` guarda el instante en UTC y lo muestra en la zona de la sesión, que evita el clásico "se me desplazó una hora". |
| `TaskPriority` | `varchar(10)` + `CHECK` | Un enum de PostgreSQL sería más estricto, pero complica los cambios de esquema y el `ALTER TABLE`. El `CHECK` cubre lo mismo. |
| `boolean` | `boolean` | Los booleanos de PostgreSQL son de tres estados (`true`, `false`, `NULL`). Aquí la columna es `NOT NULL`, así que solo hay dos. |

### Sobre `timestamp` y `timestamp with time zone`

PostgreSQL tiene dos tipos parecidos y la diferencia importa:

- `timestamp without time zone` guarda un **texto de reloj**: "2026-01-01 10:00".
  No sabe en qué zona estaba ese momento.
- `timestamp with time zone` guarda un **instante**: 2026-01-01T10:00Z. Al
  mostrarlo, lo convierte a la zona de la sesión.

Para un servidor de tareas que se puede usar desde varias zonas horarias, lo
correcto es `with time zone`. Hibernate mapea `java.time.Instant` a
`timestamp(6) with time zone` de forma automática, que es exactamente lo que
hace este esquema.

## 4. Índices

| Índice | Tipo | Columnas | Para qué sirve |
| --- | --- | --- | --- |
| `tasks_pkey` | PRIMARY KEY (btree) | `id` | Búsqueda por identificador y orden por `id`. |
| `tasks_priority_check` | CHECK | `priority` | No es un índice: es la restricción que impide valores desconocidos. |

Los índices no se crean a mano. La tabla tiene una única consulta con filtros
y paginación, y con los datos de un proyecto de práctica el planificador
secuencial es el más rápido. Crear índices sin medir es una forma de hacer la
base de datos más lenta de escribir para no ganar nada.

> **Cuando la tabla crezca**, los índices que habrá que añadir son:
> `CREATE INDEX idx_tasks_completed ON tasks (completed);` para el filtro de
> estado, y uno compuesto sobre `(completed, created_at DESC)` para el listado
> paginado. Está anotado en el [alcance](SCOPE.md) como trabajo futuro.

## 5. Consultas que hace la aplicación

Todas se resuelven en PostgreSQL, nunca en memoria. Ver
[ADR-0010](adr/0010-pagination-and-filtering-in-the-repository.md).

### Listado

```sql
SELECT t.id, t.title, t.description, t.due_date, t.priority,
       t.completed, t.created_at, t.updated_at
FROM tasks t
WHERE (:completed IS NULL OR t.completed = :completed)
  AND (:priority  IS NULL OR t.priority  = :priority)
  AND (lower(t.title) LIKE :pattern ESCAPE '\'
       OR lower(t.description) LIKE :pattern ESCAPE '\')
ORDER BY t.completed ASC, <criterio> <sentido>, t.id DESC
LIMIT :size OFFSET :offset;
```

Hibernate no escribe `:parametro IS NULL` literalmente: omite con `AND` el
filtro que no se ha pedido, así que una petición sin parámetros acaba siendo
un `SELECT ... ORDER BY ... LIMIT ...` limpio.

El `ORDER BY` tiene tres niveles:

1. `t.completed ASC` — **las completadas siempre al final**, sea cual sea el
   criterio elegido. Es una decisión de producto, no del azar.
2. El criterio pedido, con su sentido:

   | Criterio | Columna | Sentido | Por qué |
   | --- | --- | --- | --- |
   | `CREATED_AT` | `created_at` | `DESC` | Lo más nuevo primero. Es el valor por defecto. |
   | `UPDATED_AT` | `updated_at` | `DESC` | Lo modificado más recientemente primero. |
   | `DUE_DATE` | `due_date` | `ASC` | La fecha límite más cercana primero. |
   | `TITLE` | `title` | `ASC` | Orden alfabético. |
   | `PRIORITY` | expresión `CASE` | `ASC` | De más urgente a menos urgente. |

3. `t.id DESC` — desempate. Sin él, dos tareas con el mismo valor pueden
   cambiar de posición entre dos peticiones y la paginación mostraría alguna
   dos veces.

### El orden por prioridad

La prioridad se guarda como texto (`LOW`, `MEDIUM`, `HIGH`), así que un
`ORDER BY priority DESC` daría `MEDIUM`, `LOW`, `HIGH`: el orden alfabético,
que no es el que espera nadie que pide "ordenar por prioridad".

Por eso el orden usa una expresión que traduce cada prioridad a su rango:

```sql
CASE WHEN t.priority = 'HIGH'   THEN 0
     WHEN t.priority = 'MEDIUM' THEN 1
     ELSE 2 END
```

`ASC` sobre ese rango deja primero `HIGH`. La expresión es estándar y
funciona igual en PostgreSQL y en H2, así que los tests ven el mismo
comportamiento que la aplicación.

### Búsqueda por texto

El texto se busca en el título **y** en la descripción, sin distinguir
mayúsculas, con `lower(...)` y `LIKE '%texto%'`.

Los comodines de `LIKE` (`%` y `_`) se escapan con `escapeLike()`, de modo que
buscar `%` busca literalmente un porcentaje en lugar de devolver todo.

El comodín inicial impide usar un índice normal sobre el título. Para un
proyecto de este tamaño es irrelevante; si algún día hiciese falta, la
solución es un índice trigram (`pg_trgm`), no reescribir la búsqueda.

### Estadísticas

```sql
SELECT COUNT(*)                                FROM tasks;
SELECT COUNT(*)                                FROM tasks WHERE completed = TRUE;
SELECT COUNT(*)                                FROM tasks WHERE completed = FALSE;
SELECT COUNT(*)                                FROM tasks
       WHERE completed = FALSE AND due_date < CURRENT_DATE;
```

Las cuatro se ejecutan como consultas separadas en lugar de una sola con
`FILTER` o `CASE`, porque así cada una es trivial de leer y el repositorio no
necesita SQL específico de PostgreSQL.

## 6. Migrar el esquema

### Estado actual

Hibernate crea y actualiza la tabla al arrancar (`ddl-auto=update`). Es
suficiente para desarrollo y para el proyecto de práctica, pero **no** para
producción: `update` no sabe deshacer cambios, no registra qué se ha aplicado
y dos instancias arrancando a la vez pueden pelearse por el esquema.

### Migración prevista

El [ADR-0009](adr/0009-flyway-over-ddl-auto.md) describe el paso a Flyway:

```
backend/src/main/resources/db/migration/
├── V1__create_tasks_table.sql
├── V2__add_priority_and_updated_at.sql
└── V3__create_indexes.sql
```

Con Flyway:

- `spring.jpa.hibernate.ddl-auto` pasa a `validate`: la aplicación **comprueba**
  que el esquema es el esperado y falla si no coincide, en lugar de modificarlo.
- Cada migración es un fichero versionado que **nunca** se modifica una vez
  aplicado. Para corregir una migración que ya está en producción se crea otra
  nueva con la versión siguiente.
- El esquema deja de depender del orden de arranque de las instancias.

### Entorno de desarrollo

Cuando se incorpore Flyway, la base de datos de desarrollo hay que **recrearla**
para que la primera migración se aplique sobre una tabla vacía:

```bash
docker compose down -v
docker compose up -d
```

`-v` borra también el volumen, que es donde viven los datos.

## 7. La base de datos de desarrollo

`docker-compose.yml` levanta PostgreSQL 17 con un `healthcheck`, para que el
backend no arranque antes de que la base de datos acepte conexiones.

| Variable | Valor por defecto | Para qué |
| --- | --- | --- |
| `DB_URL` | `jdbc:postgresql://localhost:5432/taskdb` | Cadena de conexión JDBC. |
| `DB_USERNAME` | `taskuser` | Usuario de la aplicación. |
| `DB_PASSWORD` | `taskpassword` | Contraseña de la aplicación. |
| `DDL_AUTO` | `update` | Comportamiento de Hibernate sobre el esquema. |

Las credenciales son de desarrollo y están en `.env.example`, no en el
repositorio con valores reales. Ver
[ADR-0005](adr/0005-environment-variables-for-secrets.md).

### Verificar el esquema a mano

```bash
psql -h localhost -U taskuser -d taskdb -c "\d tasks"
psql -h localhost -U taskuser -d taskdb -c "SELECT * FROM tasks ORDER BY id DESC LIMIT 10;"
psql -h localhost -U taskuser -d taskdb -c "SELECT priority, completed, COUNT(*) FROM tasks GROUP BY 1, 2;"
```

## 8. Copias de seguridad

No hay ninguna automatización. Con una sola tabla, una copia es un `pg_dump`:

```bash
pg_dump -h localhost -U taskuser -d taskdb -f taskdb-$(date +%Y%m%d).sql
```

Y se restaura con:

```bash
psql -h localhost -U taskuser -d taskdb -f taskdb-20260101.sql
```

Un proyecto de práctica no necesita más. Cuando lo necesite, la respuesta
habitual es `pg_dump` diario con retención, o el servicio de copia gestionado
del proveedor.
